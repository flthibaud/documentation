Un fichier YAML dans `.github/workflows/`, exécuté par GitHub sur une machine jetable à
chaque événement du dépôt.

Les pages qui suivent partent de deux workflows réels : celui de **Signet** (Go + React,
build Docker, image sur GHCR, release taguée) et celui de **ce site** (Astro → GitHub Pages).

## Le vocabulaire

| Terme | Ce que c'est |
| --- | --- |
| **workflow** | un fichier `.yml`, déclenché par un événement |
| **job** | un groupe d'étapes, sur **sa propre machine neuve** |
| **step** | une étape : soit une commande shell (`run`), soit une action (`uses`) |
| **action** | un bout de code réutilisable publié sur un dépôt (`actions/checkout@v4`) |
| **runner** | la machine qui exécute un job (`ubuntu-latest`, chez GitHub) |

## Le modèle mental

Deux idées suffisent à débloquer 90 % de la lecture d'un YAML :

1. **Un job = une machine vierge.** Rien ne survit d'un job à l'autre : ni les fichiers, ni
   les dépendances installées, ni les variables. Deux jobs qui doivent partager quelque
   chose passent par un artefact. C'est ce qui explique la moitié des lignes d'un workflow.
2. **Les jobs tournent en parallèle par défaut.** `needs:` est ce qui les remet en ordre.
